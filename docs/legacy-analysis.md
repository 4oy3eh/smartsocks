# Разбор legacy-кода SmartSocks

Источники: `4oy3eh/SensorApplication` (Android, Java, 13 коммитов, сент. 2022) и `4oy3eh/Sensor` (старые
копии `MainActivity`/`Config`/`Visual` в `.txt`, прошивки там нет). Клоны лежат в `legacy/` — только для чтения.

## 1. Транспорт: это Classic Bluetooth SPP, не BLE

- `createInsecureRfcommSocket(1)` через reflection → RFCOMM канал 1 (Serial Port Profile).
- Устройство должно быть заранее спарено (`getBondedDevices()`), сканирования нет.
- MAC из «Last setup»: `00:16:A4:48:8E:E6`, имя `Block 3`.
- **Следствие:** iOS не поддерживает SPP без MFi → кроссплатформенность возможна только при BLE-прошивке.
- На Windows спаренное SPP-устройство появляется как COM-порт → протокол можно отлаживать с ПК (Python + pyserial).

### Команды (ASCII, оканчиваются `\r`)

| Команда | Смысл |
|---|---|
| `BT^START\r` | начать стрим |
| `BT^STOP\r` | остановить стрим |
| `BT^TRES\r` | сбросить таймстамп устройства |
| `BTS1=n\r`, n=0..8 | частота: n=0 → 10 Гц, иначе 25·n Гц (до 200 Гц) |
| `BTS2=n\r`, n=0..9 | диапазон измерения: 2·2ⁿ кОм (0 → 2 кОм … 9 → 1024 кОм) |

Порядок в legacy подозрительный: `START` → `STOP` → `BTS2` → `BTS1` → `TRES` (START второй раз не шлётся).
Логичный порядок: `STOP` → `BTS2` → `BTS1` → `TRES` → `START`. **Проверить на железе.**

### Пакет (47 байт)

```
[0]      0xF0   start byte
[1..28]  ???    не декодируются (вероятно таймстамп, возможно доп. каналы) — нужен дамп
[29..44] 8 × uint16 little-endian — сопротивление датчиков 1..8 (используются 6)
[45]     ???    (возможно checksum)
[46]     0x55   stop byte
```

Сопротивление, Ом: `R = raw * 2^(BTS2 - 5)` (таблица `0.03125, 0.063, …, 16.0`).
Верхняя граница диапазона: `2000 * 2^BTS2` Ом.

## 2. Обработка сигнала в legacy

Датчики — FSR (force-sensitive resistor): **чем сильнее давят, тем меньше сопротивление**.

1. **Калибровка**: нога поднята → запоминаем `R0[i]` (сопротивление без нагрузки).
2. **«Нормализация»**: `n[i] = max(0, R0[i] - R[i])`.
3. **Процент**: `p[i] = n[i] / R0[i] * 100` — доля падения сопротивления.

Формулы `1/R` в коде **нет** (вы помните её правильно как идею, но в legacy её не реализовали).

## 3. Center of Pressure в legacy

Датчики заданы углами с α = 75°: `s1=α, s2=180−α, s3=0°, s4=180°, s5=360−α, s6=180+α`;
s3/s4 дополнительно умножены на `cos α`. Если раскрыть тригонометрию — это просто сетка 2×3:

| Датчик | x | y | Положение |
|---|---|---|---|
| 1 | +0.259 | +0.966 | перед |
| 2 | −0.259 | +0.966 | перед |
| 3 | +0.259 | 0 | середина |
| 4 | −0.259 | 0 | середина |
| 5 | +0.259 | −0.966 | пятка |
| 6 | −0.259 | −0.966 | пятка |

Используемая формула (`xValueMethod2`/`yValueMethod2`): `COP = Σ (n[i]/R0[i]) · pos[i]` — **без деления на Σ весов**.
Это не центр давления: при одинаковой форме нагрузки результат масштабируется с силой нажатия и может выйти
за пределы стопы (давим на s1 и s3 по 100% → x = 0.518, вне стельки).

### Как правильно

FSR: `R ≈ k / F`, т.е. **проводимость `G = 1/R` примерно линейна по силе**. Поэтому:

```
w[i]  = max(0, 1/R[i] − 1/R0[i])          // прирост проводимости ≈ сила на датчике
W     = Σ w[i]                            // ≈ суммарная нагрузка на стопу
COP   = Σ w[i]·pos[i] / W,  если W > порог // иначе нога в воздухе → COP нет
```

Дополнительно: позиции датчиков — из реальной геометрии стельки (мм), а не из углов; опционально
поканальная калибровка по известному весу; фильтр (EMA / 1€-filter) на COP.

Для двух ног: доля нагрузки `L% = W_L / (W_L + W_R)`; общий COP —
`(W_L·COP_L + W_R·COP_R) / (W_L + W_R)` в общей системе координат (нужна ширина стойки).

## 4. Почему лагает

1. **Busy-wait**: `while(true) { if (available() > 0) ... }` — крутит ядро CPU на 100 % без блокирующего `read`.
2. **Флуд UI-потока**: на *каждый* пакет (до 200 Гц) `runOnUiThread` → очередь растёт быстрее, чем экран
   рисует 60 Гц → нарастающая задержка.
3. На каждый пакет — переключение видимости 18 `ImageView` и `setImageBitmap` целиком.
4. COP рисуется в bitmap, который не очищается (только раз в 50 кадров).
5. Аллокации на каждый пакет: `new byte[]`, `Arrays.copyOfRange` ×6, boxing `ArrayList<Float>`.
6. `ArrayList` X/Y пишется из BT-потока и читается/чистится из UI без синхронизации → гонки
   (отсюда `catch (NullPointerException)` повсюду).

## 5. Баги и плохие практики

- Всё состояние — `static` поля Activity (`thread`, `isLeft`, `textSensor[]`) → утечки, одна нога на процесс.
- Режим двух ног (`visual_two.java`) целиком закомментирован; `MainActivity` собирает `both`, но `Visual` его не умеет.
- Правая нога: стрелки сравнивают `[3]` с `[4]` вместо `[2]`; при зеркалировании красная полоса
  отражается дважды, жёлтая — ни разу.
- Цвета инвертированы относительно комментариев («green» видна при минимальном нажатии).
- `getSensorPercent()` делит на `R0 = 0` для датчиков 7–8 → `NaN/Infinity`.
- `calibrationSum()` использует `.count()` (вернёт 8, а не сумму).
- **Запись данных фактически сломана**: в `ConnectedThread` запись под `if(false)`, в файл пишутся только `---`;
  путь `/sdcard/Sensor/data` + `WRITE_EXTERNAL_STORAGE` не работают на Android 10+.
- `targetSdk 30`, нет `BLUETOOTH_CONNECT/SCAN` → на Android 12+ падение/SecurityException.
- Имя/MAC устройства вырезаются из строки списка через `substring` по фиксированным смещениям.
- Мёртвый код: `old*`, `visual_copy`, `visual_two`, `test`, `ConnectedThread_copy`, пустой `ValueList`,
  NDK C++ «Hello from C++» (тормозит сборку ни за что).
- Тестов нет (только шаблонные `Example*Test`).

## 6. Что неизвестно и нужно выяснить на железе

- Байты 1–28 и 45 пакета (снять сырой дамп, сопоставить с `BT^TRES`).
- Реальная раскладка датчиков на стельке (какой физический датчик = индекс 1..6) и их координаты в мм.
- Корректная последовательность команд старта.
- Это точно тот же модуль (SPP), или есть/планируется BLE-прошивка?
- Можно ли менять прошивку (тогда можно добавить seq-номер, CRC, BLE).
